# Skillify（技能化）

将当前会话的可重复过程捕获为可重用的技能。

各 harness **平级**：先确认技能最终给哪个平台用，再按该平台的目录和工具名落盘。不存在默认平台。

## 使用场景

当您想要将可重复的过程捕获为可重用的技能时使用。在您想要捕获的过程结束时调用。示例：
- "使其成为一个技能"
- "捕获此工作流"
- "技能化"
- "创建技能"
- "保存这个流程"

## 参数

- `description`（可选）：您想要捕获的过程描述

## 步骤 0：确认目标平台

技能给哪个 harness 用，直接决定保存路径、工具名和 frontmatter 约束。**先问用户，不要替用户默认**。

用当前 harness 的提问能力（DSH：`ask_user_question`；OpenCode：`question`；其他 harness 用其等价方式）问：

> 这个技能要在哪个 harness 里使用？

选项：
- **当前会话所在 harness**（最省事，但仍需用户确认，不默认选中）
- **DSH**
- **OpenCode**
- **Claude Code**
- **多平台通用**（放便携目录，只写各平台都成立的写法）

补充：
- 用户选"当前会话"时，先判断当前 harness（环境变量、项目目录、由哪个 CLI 启动），再走对应分支。
- 用户说"随便/通用"时，选便携目录，并避免写入任何平台专属的工具名或字段。
- 用户要适配的平台不在上表时，先查该平台文档或问用户，按"能确认多少写多少"处理，不臆造。

## 平台对照（对称，无默认位）

| 维度 | DSH | OpenCode | Claude Code |
|---|---|---|---|
| 项目级技能目录 | `<项目根>/.dsh/skills/<name>/SKILL.md` | `.opencode/skills/<name>/SKILL.md` | `.claude/skills/<name>/SKILL.md` |
| 个人级技能目录 | `~/.dsh/skills/<name>/SKILL.md` | `~/.config/opencode/skills/<name>/SKILL.md` | `~/.claude/skills/<name>/SKILL.md` |
| 便携目录（多平台共用） | `<项目根>/.agents/skills/<name>/SKILL.md` | 同左 | 同左 |
| 向用户提问 | `ask_user_question` | `question` | 以该平台文档为准 |
| 独立上下文执行 | `subagent` / `subagent_fork` | Task subagent | Task subagent |
| 生效方式 | 监听技能根，写后即刻生效 | 以该平台加载时机为准 | 以该平台加载时机为准 |

> 未列出的平台（Codex、Gemini CLI、Cursor 等）：走便携目录 + 指令文件清单，写法保持通用。
> 无法确认的单元格写"以该平台文档为准"，不要沿用其他平台的名字。

## 技能格式

**各平台都成立的最小集**（优先按它写）：
- 目录名 = 技能名，kebab-case
- `SKILL.md` + frontmatter 的 `name` 和 `description`
- description 写清"做什么 + 什么时候用"——多数平台只靠它触发
- 正文按步骤组织，每步带可验证的成功标准

**平台专属约束按目标平台追加**，例如目标包含 DSH 时：
- catalog 只呈现 `name` + `description`，description 默认截断到 500 字符
- 可选字段：`whenToUse`、`metadata`、`disable-model-invocation`、`user-invocable`
- 布尔必须写成 YAML 布尔；非法值（字符串、驼峰键）会让整个技能被丢弃
- 只扫描一层：`<root>/<name>/SKILL.md` 或扁平的 `<root>/<name>.md`
- 项目根 = 最近含 `.git` 的祖先目录

其他平台的字段与目录以自己的文档为准；不确定就先读文档或问用户，**不要照搬 DSH 的字段**。

## 运行模式（通用）

- 技能通常是"内联注入当前 agent 的指令"，不是可执行程序，一般不存在"技能分叉运行"。
- 若被捕获的过程需要独立上下文：在步骤里写明用该平台的子代理（DSH：`subagent` / `subagent_fork`；OpenCode / Claude Code：Task），而不是假设技能会 fork。
- 需要中途人工引导：写成内联步骤 + 提问检查点。
- 是否支持"人用斜杠命令直接调用"由目标平台决定（DSH 用 `user-invocable`），不确定就不要写。

## 您的任务

### 步骤 1：分析会话

在提问之前，分析会话以识别：
- 执行了什么可重复的过程
- 输入/参数是什么
- 不同的步骤（按顺序）
- 成功的产物/标准（例如不仅仅是"编写代码"，而是"一个 CI 完全通过的开放 PR"）
- 您在哪里纠正或引导了过程
- 需要哪些工具和权限
- 使用了哪些子代理（按平台各自的形态描述）
- 目标和成功的产物是什么

### 步骤 2：采访用户

使用当前平台的提问工具。重要说明：
- 所有问题都使用提问工具，不要用纯文本提问。
- 每轮迭代直到用户满意为止。
- 用户总能自定义填写，所以不要添加"需要调整"/"我提供编辑"这类占位选项，只给实质性选择。

**第 1 轮：目标平台 + 高层确认**
- 先确认目标平台（见步骤 0），这决定后续所有路径与格式。
- 根据您的分析建议技能名称和描述。让用户确认或重命名。
- 建议高层目标和技能的具体成功标准。

**第 2 轮：更多细节**
- 将您识别的高层步骤作为编号列表呈现。告诉用户您将在下一轮深入细节。
- 如果您认为技能需要参数，根据您观察到的内容提出参数。确保您理解有人需要提供什么。
- 如果不明确，请问这个流程应该在**当前对话内联执行**，还是需要**独立的子代理上下文**。需要隔离噪声、且不需要中途输入 → 后者；需要用户中途引导 → 前者。
- 询问技能应该保存在哪里。根据上下文提供默认建议（特定于仓库的工作流 → 项目，跨仓库个人工作流 → 个人），路径按第 0 步选定的平台给：
  - **本项目**（该平台的项目级技能目录）
  - **个人**（该平台的个人级技能目录）
  - **便携**（`<项目根>/.agents/skills/`，仅当要多平台共用）

**第 3 轮：分解每个步骤**
对于每个主要步骤，如果不是非常明显，请问：
- 此步骤为后续步骤产生什么？（数据、产物、ID）
- 什么证明此步骤成功了，我们可以继续？
- 是否应该让用户确认后再继续？（特别是对于不可逆的操作如合并、发送消息或破坏性操作）
- 是否有任何步骤可以独立并行运行？（例如同时发布到 Slack 和监控 CI）
- 技能应该如何执行？（直接执行 / 子代理 / 批量编排，按目标平台的对应原语写）
- 有什么硬约束或硬偏好？必须或不应该发生什么？

您可以在这里进行多轮提问，特别是如果有超过 3 个步骤或很多澄清问题。根据需要迭代。

重要提示：特别注意用户在会话中纠正您的地方，以帮助为您的设计提供信息。

**第 4 轮：最后的问题**
- 确认何时应该触发此技能，并建议/确认触发短语。多数平台的触发只看 description，所以要收集用户真实会说的话。（例如：当用户想要将 PR cherry-pick 到发布分支时使用。示例："cherry-pick 到发布"、"CP 此 PR"、"hotfix"。）
- 如果目标平台支持由人直接调用（如 DSH 的 `user-invocable`），确认是否需要。
- 您还可以询问任何其他需要警惕的事情，如果仍然不清楚的话。

一旦有足够的信息就停止采访。重要提示：对于简单的过程不要问太多！

### 步骤 3：编写 SKILL.md

在第 2 轮用户选择的位置创建技能目录和文件。

使用此格式（通用最小集，再按目标平台追加字段）：

```markdown
---
name: {{技能名称，kebab-case，与目录名一致}}
description: {{单行描述，含"何时使用"的触发短语}}
---

# {{技能标题}}
技能描述

## 使用场景
{{何时应该触发此技能的详细描述，包括触发短语和示例用户消息}}

## 参数
- `$参数名`: 此输入的描述

## 目标
明确陈述此工作流的目标。如果您有明确定义的产物或完成标准，最好。

## 步骤

### 1. 步骤名称
在此步骤中要做什么。具体且可操作。适当时包括命令。

**成功标准**：始终包含此项！这表明步骤完成，我们可以继续。可以是一个列表。

...
```

**每步注释**：
- **成功标准**是每个步骤必需的。这帮助模型理解用户对其工作流的期望，以及它应该何时有信心继续。
- **执行**：`Direct`（默认）、子代理（按平台写：DSH `subagent` / `subagent_fork`；OpenCode / Claude Code 用 Task）、批量编排（若平台支持），或 `[human]`（用户执行）。如果不明确，则不需要指定。
- **产物**：此步骤为后续步骤产生的数据（例如 PR 号、commit SHA）。仅在后续步骤依赖时包含。
- **人工检查点**：何时暂停并让用户继续。包括不可逆操作（合并、发送消息）、错误判断（合并冲突）或输出审查。
- **规则**：工作流的硬规则。会话中的用户纠正尤其有用。

**步骤结构技巧**：
- 可以并发运行的步骤使用子编号：3a、3b
- 需要用户操作的步骤在标题中包含 `[human]`
- 保持简单技能简单 — 2 步技能不需要在每个步骤上注释

### 步骤 4：确认和保存

在写入文件之前，将完整的 SKILL.md 内容作为 markdown 代码块输出到您的回复中，以便用户可以查看。然后使用提问工具询问确认，使用简单的问题如"这个 SKILL.md 看起来可以保存吗？"——保持问题简洁。

写入后读回校验（`read` 一次目标文件），只校验**目标平台确实支持的**内容：
- `name` 是 kebab-case，且与目录名一致
- `description` 是单行，包含触发短语
- 该平台的字段是否合法（目标包含 DSH 时，布尔必须是 YAML 布尔、description 不超过 500 字符）

然后告诉用户：
- 技能保存的位置
- 该平台如何触发它（自动触发 / 是否支持由人直接调用）
- 该平台的生效时机（DSH 是写后即刻生效；其他平台以其加载时机为准）
- 他们可以直接编辑 SKILL.md 来优化它

## 示例

用户说："把刚才的代码审查流程做成一个技能"

**第 1 轮**：
- 目标平台：用户确认"当前会话这个"（示例为 DSH）
- 建议名称：`code-review`
- 建议描述：代码审查工作流，自动检查代码质量、运行测试、生成审查报告
- 目标：确保代码符合项目规范且所有测试通过

**第 2 轮**：
- 步骤：1) 运行 lint → 2) 运行测试 → 3) 生成审查报告
- 参数：`target`（要审查的文件或目录）
- 运行模式：内联（每一步之后要让用户确认修复范围）
- 保存位置：本项目（`<项目根>/.dsh/skills/code-review/SKILL.md`）

**第 3 轮**：
- 步骤 1 产物：lint 结果
- 步骤 2 成功标准：所有测试通过
- 步骤 3 产物：审查报告文件路径

**第 4 轮**：
- 触发短语："审查代码"、"code review"、"检查代码质量"
- 允许人直接调用（DSH 下设置 `user-invocable`）

## 常见问题

- **用户中途取消**：保存已确认的部分，告知用户可稍后继续
- **参数提取失败**：使用提问工具询问用户具体值
- **步骤不明确**：请用户提供更多细节或示例
- **用户说不清要哪个平台**：不要猜。给"当前会话 / 多平台通用"两个最小选项让用户二选一；通用方案只写各平台都成立的字段
- **写完没被识别**：先核对目标平台的目录层级和 frontmatter 合法性（DSH 对非法 frontmatter 是整体丢弃，没有逐条报错）
