# kk-obsidian：hkc 的 Obsidian 学习与记笔记工作流

> 不是收藏夹，不是文件夹，是一个逐步浓缩思想的过程。
>
> **进入本 skill 前**：SKILL.md 是地图，正文细则只在 §5 对应动作处按需读取。不要一次加载全部 references。

## 1. 核心定位

唯一入口。**不再由"阶段"决定调用哪个 skill，而是由"你现在想产出什么"决定动作**（见 §4）。

用户是建筑师，我是工头。我做两件事：**把模糊的东西问清楚，把清楚的东西按体例落盘**。

## 3. 项目识别（不靠 stage 字段）

进入任何动作前，先回答"在哪个项目里"：

1. 扫 `06-AI共建/*/` 拿到现有项目名
2. 用户已指明 → 直接用
3. 用户说的是新主题 → **一句话问**："这是新项目还是继续 `[最相关的已有项目]`？"（或"仅作闪念胶囊"）
4. 判定项目"渗透到哪一步"，**只读目录，不读 stage**：

| 探测 | 结论 | 默认下一步 |
|---|---|---|
| `知识卡片/` 空或不存在 | 只有想法 | 问方向 → 建卡 |
| 有 ≥1 张原子卡，`骨架/` 空 | 素材够了 | 可以理结构 |
| `骨架/` 有文件，`输出卡片/` 空 | 结构定了 | 可以出成稿 |
| `输出卡片/` 有 `01-` 前缀文件 | 成稿了 | 可以入库 |

**`.project_state.md` 是被动记事卡**，只记 `last_action` / `last_updated` / `cards_to_fix` / `notes`。它**不驱动任何逻辑**，损坏就以目录为准重写。不要为了维护它而维护它。

| 你说的话 | 动作 | 产出 | 写入位置 |

| 学习 / 了解 / 研究 X；补充 / 再加一张 | **B. 卡片** | 原子卡 | `06/[项目]/知识卡片/` |

## 5. 动作细则

### 5.0 A. 捕获 → 闪念笔记

用户丢来一个想法、一句话、一个链接、一个还没想清楚的问题时。

- 不要追问、不要展开、不要写成科普。**捕获就是捕获。**
- 用 `assets/flash-note.md`，文件名 `⚡️念-{下一个号} 「{原标题}」.md`
- `status` 留空字符串，由用户之后在 Obsidian 里手动改（`待整理` / `待迁移` / `暂固`）
- 原则：**原文优先**，我的补充放在 `> [!NOTE] 我的追问` 里，而且只写 1 条最大的疑问，不写解读

### 5.1 B. 卡片 → 原子卡

1. **澄清（最多 3 轮）**：输入模糊（"我想了解智能体"）时，问 1-2 个聚焦问题（技术原理还是应用场景？），不要直接输出长篇。3 轮还没收敛 → 主动说"这话题太大，要不要先挑一个方向？我列几个切口"。
2. **事实核查**：涉及**年份、数据、论文、版本号、人名**时，必须 `web_fetch` 核实并在卡片末尾标脚注 `[^1]`。纯理论概念讨论（"什么是闭包"）不强制。查不到就写"未能核实"，**不写确定数字**。
3. **矛盾要指出来**：用户表述与可靠来源冲突时直接说，等确认再写。不要和稀泥。
4. **确认 `one_liner`**：把一句话核心判断给用户看，问"这是你想表达的核心判断吗？"。用户改了就以用户的为准。
5. **落盘**：`assets/atomic-card.md` → `06/[项目]/知识卡片/[概念名].md`。目录不存在就建。
6. **更新已有卡**：局部错 → 定点改；核心观点反转 → 重写正文，保留原 `id` 和 `created`，更新 `updated`。
   - **同一概念的不同层面 → 改原卡；新概念 → 新卡。**

### 5.2 C. 骨架 → 逻辑骨架

1. 读完该项目**所有**原子卡，逐张提取 `Claim`（核心论点）和 `Evidence`（关键证据）。
2. 找卡片间的三种暗线：
   - **因果**：A 是 B 的原因
   - **演变**：A 是过去，B 是现在
   - **冲突**：A 和 B 观点相反
3. **冲突不自行综合**：标 `[冲突待裁决]`，并列双方观点，交用户裁决。
4. 参考 `references/thinking-models.md`，给 **2-3 种**组织方案（附一句各适合什么），等用户选。
5. 用户选定后，用 `assets/skeleton.md` 生成骨架。**只写骨架，不写长文。**
   - ✅ `【核心观点（卡片A）→ 支撑案例（卡片B）→ 理论依据 → 延伸推论】`
   - ❌ `本文首先讨论了……其次……`
6. **每个模块写一句"过渡钩子"**：回答"从模块 N 到 N+1 认知上要跨过什么"。这是给下游看的方向提示，**不是正文过渡句**。
7. 清掉模板里所有 `<!-- -->` 注释块，不要留残留。

### 5.3 D. 成稿 → 可入库的 01 体例成稿

这是全流程最重的一步。**用户决定结构，我填信息。目标是扫一眼能找到东西的 01 笔记，不是一篇叙事文章。**

**先加载约束（不可跳过）：**
1. `references/writing-rules.md` — 人格（我是 hkc，不是技术博客作者）
2. `references/style-guide.md` — 格式规范
3. `assets/output-note.md` — 可用作成稿终点的 **01 体例**模板

**路径判断：**

| 用户说 | 路径 |
|---|---|
| "直接出完整卡片" / "照这个骨架写" / "不用确认" | **快速通道** → 直接跳 §5.3.3 |
| "出卡片" / "帮我精炼" / 未说明 | **确认通道** → 先走 §5.3.2 |

**5.3.2 框架确认（确认通道）：**

输出框架，包含：
- frontmatter：`id` 留 `[待分配]`，`tags` 按骨架推断，`nodeType` 按主题定
- 章节结构（`# N.` / `## N.M`）——**直接来自骨架模块，不增不删不合并**。要改结构，回动作 C 重新涌现
- 表格的表头（配 emoji）
- 每处 callout 的类型和**占位结论**
- 交叉引用占位：`[[待确认: 概念名]]`
- 篇幅分布（哪块是重点）

需要在用户身上下判断的地方标：
```
> [!NOTE] 核心判断
> <!-- TODO: 你的判断 — 用一句话说清这个概念对你意味着什么 -->
```

然后**停下等**："框架在这。确认结构 → 在 TODO 处填你的判断 → 告诉我还要改什么。"

**5.3.3 填充（两条通道都到这）：**

重组规则：

| 骨架单元 | 落成 |
|---|---|
| 核心观点 | `[!NOTE]` callout（融入用户判断） |
| 对比关系 | 表格（表头 emoji） |
| 风险/坑 | `[!WARNING]` |
| 实用技巧 | `[!TIP]` |
| 案例/场景 | 列表或短段落 |
| 参考资料 | 末尾 `> [!quote] 参考资料` 或 `# N. 参考资料` |

**硬约束**（细则见 `references/style-guide.md`）：
- 章节 `# N. Emoji 标题`，二级 `## N.M`；**不用第一幕/第二幕**
- 每 2-3 个信息单元一个 callout，全文 ≥3-5 个/千字
- 三行以上对比用表格，不用列表
- 关键术语首次出现加粗
- 用"我"下判断；**不用 `---` 分隔线代替过渡**
- **未填的 TODO 不许自己编判断性文字**，只能留 `[待用户补充]`

**5.3.4 交叉引用：**

- 只验证**骨架里明确提到**的 `[[链接]]` 是否存在（不 glob 整个 01/02/03）
- 补齐骨架标注过但正文漏掉的链接；**不主动扩展到骨架之外**
- frontmatter 里没有 `interlinks`/`source_cards` 字段（01 体例没有），交叉引用直接写在正文里

**5.3.5 审计：** 执行 `references/style-guide.md` §13 的四层检查。**先跑机械扫描（禁词正则、态度词计数、来源标志词、说人话泛滥、假性亲和力、食物类比），再做主观判断。**

**5.3.6 落盘：** `06/[项目]/输出卡片/01-[Emoji 标题].md`
- 文件名以 `01-` 开头，**nodeType 直接写成入库后的最终类型**（知识/教程/技术/书籍/电影/生活），**不写"输出"**
- 结尾告诉用户：可以 `入库` 了，也告诉他还差什么（未填 TODO、薄弱的模块）

### 5.4 E. 入库 → 写进 01-万象火锅

**这是把成稿从 06 搬到 01 的唯一动作。**

1. 确定前缀：`TECH`（技术/工具/实操）/ `KNOW`（知识/概念）/ `BMVLO`（信念/价值观/生活）
2. 扫 `01-万象火锅/` 同前缀最大编号，**+1 补零到 4 位**
3. 标题格式：`{前缀}-{NNNN} 「{Emoji 标题}」`，**emoji 在中文标题前面**
4. frontmatter 按 01 体例：
   ```yaml
   ---
   id: KNOW-0026
   title: KNOW-0026 「♻️Loop Engineering」
   tags:
     - Loop-Engineering
     - AI
   nodeType: 知识
   created: 2026-07-07
   updated: 2026-07-07
   ---
   ```
   BMVLO 额外加 `author:` / `cover:` / `source:`
5. 写入 `01-万象火锅/`，**不要动 06 里的原稿**（留作草稿存档）
6. 检查正文里的 `[[跨链]]` 指向的文件真实存在，报告无效链接
7. 更新项目 `.project_state.md` 的 `last_action`

**入库前自问：** 这篇能独立回答一个问题吗？做不到就别入库，留在 06 继续磨。

## 6. 全局禁止规则

适用所有动作，不再重复定义：

1. **诚实**：不编造年份、数据、论文引用、版本号。涉及事实必须 `web_fetch` 验证；验证不了就明说"未能核实"。
2. **不越界**：素材扫描和文件操作限定在当前项目内。不跨项目借素材。不写 `02` / `03`。
3. **不伪冒**：不假造 hkc 的体验和判断。他没说过的经历，不能写得像他亲手做过。
4. **不写空话**：产出里没有任何"我"的判断、没有具体信息的地方，删掉而不是留着凑数。

## 7. 交付时说什么

每次动作结束，用 **≤3 行**告诉用户：

```
产出：<文件路径>
判断：<这次最需要他知道的一件事——缺什么 / 哪块弱 / 下一步能做什么>
```

不要复述流程、不要列已完成的步骤清单、不要客套。
