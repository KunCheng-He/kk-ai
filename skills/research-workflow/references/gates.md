# 门禁

门禁分两层：**脚本能判的**交给脚本，**脚本判不了的**才人工复核。每次终审先跑脚本，再做人审，避免用眼睛替代 grep。

## 门禁 1：证据冻结（写作前置）

脚本：`node scripts/check-evidence.mjs <证据文件...>`

| 判据 | 说明 |
|---|---|
| 文件头存在且合法 | YAML front-matter，含 `run` / `status` / `counts` / `failures` |
| `status: complete` 且 `frozen_at` 非空 | 否则视为未冻结 |
| `counts` 与正文实际条数一致 | 按 `evidence_id` 前缀逐项核对 |
| 每条证据字段齐全 | `claim` / `source_url` / `platform` / `retrieved_at` / `confidence` |
| URL 是具体内容页 | 有路径，不是站点首页 |
| `retrieved_at` 是日期 | 格式 `YYYY-MM-DD` |
| `failures` 存在 | 无失败写 `[]`，不能省略 |

任一条不通过 → **不得派写作**。用续接（同一执行）补采，而不是新开一轮；续接不可用时按 `harness/_contract.md` 的降级规则处理。

用户明确要求先出稿时：允许，但报告标题后标注「部分完成（证据冻结于 HH:MM）」，且「数据局限」首条写明冻结时间与可能缺失的来源。

## 门禁 2：报告终审

脚本：`node scripts/check-report.mjs <报告> [--evidence <证据文件...>] [--strict]`

| 判据 | 级别 | 说明 |
|---|---|---|
| 结构完整 | 错误 | 有「摘要」「数据局限」「附录」，且顺序正确 |
| 引用可追溯 | 错误 | 正文编号都能在附录找到 |
| 附录可回溯 | 错误 | 附录编号都能在证据文件找到（传了 `--evidence` 时） |
| URL 是内容页 | 错误 | 不是首页、不是搜索页 |
| 图片可解析 | 错误 | 相对路径从报告目录能读到文件；无占位文件名 |
| 社区条目有日期 | 警告 | 缺日期且未写「发布时间未获取」 |
| 引用密度 | 警告（`--strict` 下为错误） | 每段最多一组编号 |
| 表格列数与单元格长度 | 警告 | 列数 ≤5，单元格 ≤25 字 |
| 正文配图数量 | 警告 | ≤3 张 |
| 附录编号被使用 | 警告 | 附录里有、正文没引用 |

脚本通过后仍需**人工**完成三件事：

1. **事实抽查**：抽 5 条关键结论，逐条打开来源 URL，确认来源确实支持该结论（见 `roles/fact-checker.md`）。脚本只检查"有没有引用"，不检查"引用对不对"。
2. **简报对照**：回到 `references/brief.md` 的 6 个问题，逐个确认已被回答；交付物形态符合简报。
3. **工作区卫生**：`git status --porcelain` 里除本次调研目录外没有新增未跟踪文件；临时文件不在项目根或工作区外。

## 门禁 3：交付前自检（人审，三问）

1. 报告里有没有一句话是"没有证据但我认为"？→ 标「推断」或删掉。
2. 「数据局限」是否覆盖了每一个失败的来源？→ 对照证据文件的 `failures`。
3. 数字口径是否标明（谁测的、什么环境、什么版本）？→ 竞品对比尤其容易漏。

## 失败处理顺序

1. 补证或换来源（同一执行续接，不新开）。
2. 缩小断言强度：把确定性结论改成「有证据支持的范围」。
3. 标注「部分完成」并单列「数据局限」。
4. 以上都不行 → 停止交付正式报告，向用户说明未通过项。**不得把未通过的报告描述为完整报告。**
