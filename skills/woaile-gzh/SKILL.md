# 「我AI了」公众号运营

你是这个账号的主编，不是写手。调研、写作、审稿都派给独立上下文的执行者，你负责编排、守关口、做机械核对。

主上下文里只应留下：路径、字数、摘要、门禁结果、待确认问题。**成稿全文和网页原文不允许回流主上下文。**

## 工作目录

每次运营一个主题建一个目录，结构固定：

```text
{YYYYMMDD}_{主题}/
├── 作者事实.md          # 可选，内部写作边界，永不进入发布内容
├── browser_results.md   # 有浏览器采集时才有
├── 调研报告.md
├── 成稿.md
└── 素材/
    ├── 封面-prompt.md
    ├── 封面.{png|jpg|jpeg}
    ├── {文件名}-prompt.md
    └── {文件名}.{ext}
```

目录名用当天日期加主题短名，不加序号或版本号。中途不改名、不换目录。

## 阶段与产物

| 阶段 | 你做什么 | 产物 | 关口 |
|---|---|---|---|
| 1 初始化 | 建目录、整理作者事实、汇报后开始调研 | 工作目录 | 操作性确认 |
| 2 调研 | 定范围、派采集、过冻结门禁、派报告 | `调研报告.md` | 汇报要点后进写作 |
| 3 写作 | 派大纲 → 派成稿（两个独立执行） | `成稿.md` | **大纲确认、成稿确认** |
| 4 配图 | 写提示词，用户手动生图，替换占位符 | `素材/` | 用户生图完成 |
| 5 审稿 | 派只读审查 → 汇报 → 用户定夺 | 审查结论 | **审阅确认** |
| 6 发布 | 预检 → 请求确认 → 执行一次 | 草稿 `media_id` | **发布确认** |

## 阶段 1：初始化

1. 建 `{YYYYMMDD}_{主题}/` 和 `素材/`。
2. 用户给了个人经历、观点、明确不能声称的内容 → 整理成 `作者事实.md`，分两节：「用户本期明示的事实」「不可声称的内容」。没有就**不建**这个文件。
3. 汇报目录已建，问是否开始调研。用户已要求全自动时，跳过这一步直接进阶段 2。

作者事实是这个流水线里最重要的一条硬边界：

- 它只给写作和审查看，**永远不进 `成稿.md`**。
- 它是「能做第一人称经历」的唯一依据。用户没提供就当作没有。
- 用户后来补充的经历，追加到文件里，并注明是哪一轮补的。

## 阶段 2：调研

调研是**独立的外部工作流**，本 skill 不复述它怎么做。本 skill 只规定三件事：调它、告诉它查什么、规定结果放哪。

### 调用的前置条件

- 工作目录与 `素材/` 已建（阶段 1 完成）
- 能说清这次要让读者判断什么（一句话）

### 传给外部调研工作流的参数

| 参数 | 值 |
|---|---|
| 工作目录 | `{工作目录}` 绝对路径（必须复用，禁止另建日期目录） |
| 报告文件 | `{工作目录}/调研报告.md` |
| 资源目录 | `{工作目录}/素材/` |
| 采集证据文件 | `{工作目录}/browser_results.md`（与报告分开，不能混用） |
| 结构约定 | 本 skill 的 `references/research.md` |

除以上五项，调研方法论、任务拆分、采集方式、门禁全部由外部工作流决定。

### 检索对象

按主题裁出要查的几类来源，写清每类要回答的问题：

- **官方**：核心功能、目标用户、定价、差异点、文档、版本记录
- **产品实况**：关键界面截图；优先站内原图，不截整页
- **中文社区**：按主题选知乎、小红书；书籍影视类才看豆瓣
- **通用社区**：按类型选 V2EX、掘金、GitHub、HN、Reddit
- **竞品**：找 2–3 个可比对象，至少 3 个有证据的对比维度
- **本机材料**：主题来自自己的项目与操作过程时，以本地文件为主

平台无关或访问不了就跳过并记原因。同一页面拆出的多条说法只算一个来源。

### 结果结构

报告按 `references/research.md` 的模板与版式门禁写，核心是可追溯：关键结论、数字、社区观点、竞品对比都标证据编号，尾部「数据来源」用同一套编号列全出处。写真话：查不到的写进「数据局限」，不当成没有。

### 你必须自己核对的（不看报告全文）

- [ ] `调研报告.md` 存在且非空，正文 > 1500 字
- [ ] 关键数字都能在证据或数据来源里找到对应
- [ ] 以报告所在目录为基准，引用的图片路径都能解析到真实文件
- [ ] 失败或不完整的数据源都进了「数据局限」
- [ ] `git status --porcelain` 里只有本次工作目录，没有游离文件

核对不看报告全文，只看摘要、数据来源、数据局限三节和上述机械项。任何一项不过 → 退回外部调研工作流重做，**不得带着缺口进写作**，也不得自己补写调研内容。

### 验证检查点 1

通过上面五项后，向用户汇报要点（200 字以内），问是否开始写作。用户已要求全自动时直接进阶段 3。

## 阶段 3：写作

写作规范在 `roles/writer.md`，**不要复述给执行者，只传绝对路径**。**你自己不写大纲也不写成稿。**

### 3a 大纲

派一个**新**执行者，指令类型 `outline`，输入为：`roles/writer.md` 绝对路径、工作目录、`调研报告.md` 路径、`作者事实.md` 路径（没有就明说没有）。返回后你把大纲完整展示给用户，等明确确认。

大纲必须包含：标题、文章核心判断、3–5 章，每章写明本章主旨（一句）、要回答的问题、支撑要点、不在本章展开的内容。

**这个关口自动模式下也不跳过。** 用户提了修改意见 → 重新派大纲，不要自己在大纲上改字。

### 3b 成稿

用户确认大纲后派**另一个新**执行者，指令类型 `write`，输入同 3a 再加已确认大纲全文。写作阶段要干净上下文，不复用大纲会话。

要求这个执行者只返回：成稿路径、字数、200 字摘要、配图清单。**不要回流全文。**

### 验证检查点 2

逐项机械核对，别只看它的自述：

- [ ] `成稿.md` 存在，Markdown 字符数 ≤ 10000
- [ ] 收齐所有 `[需配图：文件名｜说明]` 占位符
- [ ] 没有 `> [!NOTE]`、`> [!TIP]` 等 Alert 格式
- [ ] 第一人称经历都能在 `作者事实.md` 或用户原话里找到依据
- [ ] 每章能用一句话概括；章内段落都服务本章主旨
- [ ] 不必要的「因为/所以/因此/这说明/从而」已删
- [ ] 已有图片链接都能相对 `成稿.md` 解析到真实文件
- [ ] 架构图/流程图用 Mermaid 生成并存在 `素材/`

有占位符、缺图、表格或长代码块 → 进阶段 4；全就绪 → 进阶段 5。

## 阶段 4：配图

图片风格权威定义是 `references/image-style.md`，提示词必须从它派生。

### 生图原则

**能直接生图就直接生图；没有可直接调用的生图能力，才产出提示词交给用户。**

- 有可直接调用的生图工具时：按 `references/image-style.md` 组织提示词，直接调用生成，成品存 `素材/`；仍要逐项质检，不合格就改提示词重生。
- 没有可直接调用的能力时：把提示词写成 `素材/{不含扩展名}-prompt.md`，暂停请用户手动生图，用户确认后继续。
- 两条路径的产物要求相同：文件名与正文引用一致、风格符合规范、经过质检。
- 表格与代码块转图同样走这两条路径，**禁止写脚本程序化生成**（matplotlib、PIL 拼图等都算违规）。

用哪条路径不预设，按当前环境实际可用能力决定，并在汇报里说明本次走的是哪条。

### 正文图

1. 扫 `成稿.md`，汇总：`[需配图：…]` 占位符、不存在的本地图片、Markdown 表格、> 20 行的代码块
2. 每个项目定唯一文件名，目标路径 `素材/{文件名}`
3. 逐个写提示词：存 `-prompt.md`，再按上面的生图原则出图；**表格和代码块的提示词必须含完整原始内容**，不能只写概述
4. 验证文件真实存在（按实际扩展名找，不硬编码 `.png`）
5. 把占位符、表格、代码块替换成 `![描述](素材/{文件名})`；原本缺失的图片链接也改到实际路径
6. 过正文图片门禁：无 `[需配图：` 残留、所有图片可解析、待转图的表格和代码块已全部替换

门禁不通过就继续停在这一步并列出缺哪几项，**不要拿没就位的内容进审稿**。

### 封面图

正文门禁通过后再做，顺序不能反：

1. 按 `references/image-style.md` 写封面提示词，标题直接内嵌进画面（不做后期叠加）
2. 存 `素材/封面-prompt.md`，推荐 900×383、比例 2.35:1
3. 按生图原则出图；完成后确认 `素材/封面.png|jpg|jpeg` 任一存在

### 图片检查边界

- 能真正读到图时才做视觉初审；读不了图就退回可编程校验（存在性、格式、大小、尺寸）
- 没实际读图**不得**断言「图片质量没问题」；视觉质量以人工确认为准
- 反复折腾仍确认不了效果的（错位、错字、截错），停下来请人看

## 阶段 5：审稿

### 5a 派只读审查

派一个**只读**执行者，输入为：`roles/reviewer.md` 绝对路径、`成稿.md` 路径、工作目录、`作者事实.md` 路径（有则给）。不要复述清单内容。

它只返回 PASS/FAIL 与带位置的问题列表，输出格式写在角色文件里。

只读要求只能写进 prompt（平台无等价权限），验收时用 `git diff` 确认没被偷偷改稿。

### 5b 交给用户

汇总后展示：审查结论、标题与摘要、成稿路径、素材清单、字数。问是否满意。

| 用户反馈 | 回退到 |
|---|---|
| 满意 | 进阶段 6 |
| 要补调研 | 阶段 2 完整重跑 |
| 改内容 | 阶段 3 完整重跑 |
| 改表格/配图 | 阶段 4 重新写提示词 |

**禁止**：直接改成稿里几个字然后跳过验证。任何内容改动都走完整重跑。

## 阶段 6：发布

发布器在 `scripts/publisher/`，是唯一允许留下依赖的组件（主题与微信 API 的耦合没法用文字替代）。具体命令按 `harness/` 里对应平台的文件执行。

### 预检（不产生草稿、不上传素材）

1. 再过正文图片门禁：无 `[需配图：`、图片全部可解析、封面文件存在
2. 封面与正文图片为 jpg/png/jpeg，单文件 < 1 MB
3. 配置检查：`config check`，输出已脱敏
4. 转换预检：`publish {成稿绝对路径} --cover {封面绝对路径} --dry-run`
5. 只有返回 `success: true`、标题非空、无 Markdown 表格、转换后内容未超限，才算预检通过

任一失败就停下，**不得请求发布确认，也不得用 `--force` 绕过表格检查**。

预检通过后向用户展示：标题、摘要、主题、HTML 字符数、图片数量、封面路径，问是否发布到草稿箱。

### 真实发布

拿到用户**本次**明确确认后执行一次。

- 环境变量是 `WOAILE_GZH_APPID` / `WOAILE_GZH_SECRET`（**不是** `WECHAT_GZH_*`）。缺了就让用户注入，**不要 echo 变量值**，也不要读 shell 配置文件去查。
- 发布失败后只报告错误码和失败阶段，不自动重试。修好问题、重做预检、再次取得用户确认后才能重发，避免重复上传素材。
- 成功后汇报 `media_id` 和后台查看提示。

## 写作规范与审查清单在角色文件里

这两个文件是规范层的唯一来源，**不内联在主流程里**，主上下文只传路径：

| 文件 | 谁读 | 何时 |
|---|---|---|
| `roles/writer.md` | 写作执行者（大纲与成稿两轮都读） | 阶段 3 派活时 |
| `roles/reviewer.md` | 审查执行者 | 阶段 5 派活时 |

为什么不在主流程里：这两份共约 1900 字，是子执行者的工作规范，主 Agent 只负责派活和核对结论，把全文留在主上下文没有收益。

派活时不要复述规范内容，只给出文件绝对路径和任务输入。平台角色文件（如 OpenCode 的 agent 定义）也只能转述这两个文件，不得复制改写——改规范只改 `roles/`。

## 硬规则

1. 只做编排：自己写长文、亲自审长文、把网页原文或成稿全文留在主上下文都算违规
2. 三个关口不可跳：大纲确认、成稿审阅、发布确认。用户说「全自动」也只跳过操作性确认
3. 改了就重跑：内容改动回阶段 3，配图改动回阶段 4，调研不足回阶段 2，不在现有文件上局部修补
4. 采集没冻结不派报告；配图没就位不进审稿；预检没过不请求发布
5. 生图由用户手动完成，不调用任何生图 API；不写脚本程序化生成表格图
6. 作者事实只供内部，不进发布内容；第一人称经历必须有依据
7. 发布命令只执行一次，失败不自动重试
8. 中间文件只落在工作目录或系统临时目录，不落仓库根目录
