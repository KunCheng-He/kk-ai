# AI 工作流设计

帮助用户为一个具体目标选择最简单、可落地的协作方案。先判断问题，再映射到目标 Harness 的真实能力；不要为了使用 agent、subagent 或 workflow 而增加编排层。

## 使用边界与跨平台约定

本 skill 的跨平台性指**决策框架可复用**，不代表各 Harness 共用相同的 agent 定义、工具名、上下文传递、权限、触发机制或结果语义。

- 一般 CI/CD、构建流水线或业务流程，若与 AI agent 的任务分工/编排无关，不因出现“workflow”一词而触发。
- 用户已指定目标平台时，按该平台设计；不要再重复询问。
- 用户只问概念、取舍或跨平台原则时，直接用中立概念回答，不强制先选平台。
- 只有在建议依赖平台特定能力、路径或配置，而目标平台尚不明确时，才用当前环境实际可用的提问方式询问。不要照搬其他 Harness 的提问工具名。
- 用户要求多平台方案时，先给平台无关的设计，再列出**已核实**的平台差异。对未知或未验证的能力明确标为待核实，不把“可读某种文件”说成“平台原生支持/会自动触发”。
- 工具名、配置字段、上下文继承、同步/异步、完成通知、权限与 skill 加载方式，都必须以目标 Harness 的当前版本、当前配置和实际可见工具为准。跨 Harness 只迁移意图与设计，不复制 API 名称。
- 对不熟悉的平台，先查该平台当前官方文档或运行时工具说明；仍不能确认时，问用户或给出带边界的建议，不臆造。

## 概念模型：四个可组合的设计维度

以下是分析维度，不是每个工作流都必须具备的“四层架构”；也不保证每个平台都把它们实现成独立功能。

1. **协调者**：理解目标、安排步骤、跟踪依赖并整合交付。通常由当前主 agent 承担，不一定要另建一个 agent。
2. **委派执行单元**：把一项工作交给另一个模型、会话、进程或服务。某些平台称 subagent、agent、Task 或其他名称。不要仅凭名称推断它是否有独立上下文、是否并行、何时返回、能否续接或拥有什么权限。
3. **批量/流程编排**：将多个相互独立或重复的任务组织起来，并定义输入、阶段、聚合与失败处理。它可能是平台内置 workflow 工具，也可能是脚本；只有确认工具存在且适合后才推荐。
4. **可复用指令与固定角色配置**：
   - **Skill / 指令**：保存可重复的方法、检查清单或领域知识；加载 skill 本身不等于启动一个独立执行者。
   - **Agent / preset / 角色配置**：固定角色、模型、工具或策略的组合；其形式可能是文件、UI 配置、preset 或服务端配置。不要假设每个平台都有文件式 agent。
   - 工作流运行器解决“如何执行和聚合多项任务”，skill 解决“重复时遵循什么方法”，两者不是互相替代的概念。

### DSH 特别说明

下列语义已对照本次运行的 DSH Desktop `0.2.2-rc.2` 安装文档核对；其他版本、headless/SDK profile、自定义 Agent Preset 或 provider 可能不同，实施前重新确认。

- **委派不是仅有一个固定 API。** DSH 通过已装载的服务、provider 与模型可见工具组成委派能力。工具名可以配置；常见名称可能是 `subagent` / `subagent_fork`，但不可假设当前会话一定有它们。
- **启动结果不等于任务结果。** 常见 parent-delivery 调用会先返回已启动的子 agent 名称；完成内容随后通过完成通知到父 agent。部分本地子 agent 可续接/收消息，外部 provider 可能只执行一次。设计时要按 provider 规定结果契约，不要让父 agent 在启动响应里寻找不存在的最终结果。
- **上下文由 provider 决定。** spawn 类子 agent 可从新上下文开始；fork 类通常继承已有对话，但不会看到当前尚未完成的 turn。派发时要把缺少的目标、约束、文件路径和交付格式写进任务提示。
- **模型选择不是一概不支持。** 子 agent 的单次调用路由字段只有在工具开启相应选择、provider 支持且路由获准时才可用；没有这些条件时不要承诺按任务切模型。
- **`workflow` 与普通委派不同。** 它执行 JS 编排并扇出多个子 agent、聚合最终结果；前提是当前配置暴露了该工具。当前 DSH 文档建议仅在用户明确要求 workflow 或大型多代理编排时用它；一两项委派优先直接调用子 agent。
- **人工检查点要留在可交互的父流程。** 当前 DSH 的 live child 不能调用 `ask_user_question`；若子任务需要用户决策，应由父 agent 提问，或把未决问题作为子任务结果返回。
- **prompt 不是权限边界。** 只读要求应与实际工具可见性、provider 权限和宿主安全策略一起核对；DSH 子 agent 的权限范围在启动时确定，不能靠子 agent 自己扩大。
- **Agent Preset 不是旧式目录文件。** 当前文档将 preset 定义为由 bundle patch 声明/覆盖的组合；旧 `$DSH_HOME/.agent-presets/<id>/` 不再是当前读取方式。创建或修改 preset 前查当前版本的 Agent Preset 文档。

## 设计原则

### 1. 优先选择满足目标的最小方案

比较新增隔离/并行带来的收益，与上下文成本、延迟、token、协调开销、失败重试和冲突成本。简单、局部、依赖当前完整上下文的任务通常由当前 agent 直接完成即可。

### 2. 给委派任务明确的输入与交付契约

派发前说明目标、范围、必要上下文、不可做事项和成功标准；约定结果应包含什么（结论、关键证据、风险、文件路径或未决问题）。不要把“只回结论”或“所有中间信息都不回流”当成所有平台的固定能力；压缩低价值日志，但保留主流程决策所需的证据。

### 3. 先识别依赖，再决定并行和写入权

独立的搜索、探索或审查可以并行，但必须确认目标平台确实支持这种执行方式。写操作先划分文件/目录所有权；多个执行者可能编辑同一文件时，串行或指定唯一写入者，并由整合者复核最终 diff 与测试。

### 4. 以实际权限模型落实最小权限

只读、网络、命令执行、敏感数据和破坏性操作都按目标平台的真实权限机制配置。若只能用 prompt 约定，明确告诉用户它不是强制隔离或安全边界。

### 5. Skill、Agent 与委派任务各司其职

- 反复使用相同步骤/知识 → 考虑 skill 或项目指令。
- 需要稳定角色、工具集、模型或策略 → 考虑 agent/preset 配置。
- 需要上下文隔离、独立探索或并行 → 考虑委派任务，但先验证平台支持及成本。
- 同一流程需要扇出很多任务或重复处理大量输入 → 评估批量编排。
- 两种需求同时存在时可以组合，但不要因为 skill 或 agent 的名称推断它自动委派或隔离上下文。

## 分析流程

### 第一步：确认问题类型、目标和约束

识别用户要的是概念解释、方案评估、平台落地，还是生成/修改配置。收集必要的任务规模、重复频率、依赖关系、上下文需求、并行收益、权限风险、人工审批点与成功标准。只有平台差异会改变结论时才询问目标 Harness。

### 第二步：画出最小任务结构

将步骤标记为探索、决策、实现、验证、人工审批或重复任务；指出哪些步骤有依赖、哪些可独立执行，以及哪些会写入共享文件或产生大量中间结果。

### 第三步：选择最小充分机制

1. 当前 agent 直接完成是否足够？若任务短小、强依赖当前对话、无明显并行收益，通常不委派。
2. 哪些步骤值得隔离或并行？只把边界清晰、可独立验收的任务交出去。
3. 这是一次性任务、可复用流程，还是固定角色需求？分别评估委派、skill/指令或 agent/preset，不互相混淆。
4. 是否真的需要批量编排？规模、重复性和聚合需求明显时才考虑；一两项委派通常不需要额外编排器。
5. 当前 Harness 是否支持所需的上下文模式、并行、结果返回、模型选择和权限约束？不确定就先核对文档与工具可见性。

### 第四步：给出可执行建议

先给平台无关的决策，再给目标平台的实现映射。提供平台专属工具名、路径、字段或代码前，确认其在当前版本与配置中存在；未确认的部分使用占位符并说明验证步骤。

建议按需要输出，不必为了套模板而填满所有栏目：

```text
目标与约束：…
目标 Harness：用户指定 / 多平台 / 当前信息不足但不影响原则
推荐方案：协调者 …；委派 … / 不需要；skill/指令 …；agent/preset …；批量编排 … / 不需要
选择理由：…
上下文、权限与并发边界：…
已核实的实现方式：…
尚待核实或平台不支持的部分：…
```

## 反模式

- 只因用户说了“agent / skill / workflow”就触发或推销本 skill。
- 把 subagent、agent、Task、fork、workflow 当成跨 Harness 同义词。
- 不问需求就假设所有平台都有（或都没有）原生子 agent、skill、自动触发或批量编排。
- 把“skill 可读”当成“skill 会自动发现/触发”，或把 skill 当作独立执行者。
- 假设委派一定同步返回最终答案、一定继承全部对话，或一定完全隔离上下文。
- 声称子代理的中间信息绝不能回流；应按任务需要定义结果，而非一刀切地丢弃证据。
- 把 prompt 中的“只读”误当权限隔离；或在未核对配置时承诺工具、模型、权限能力。
- 让多个执行者无协调地同时写同一文件，或用重型 workflow 编排一两项委派。
- 在 DSH 中继续推荐已废弃的 `.agent-presets/<id>/` 目录，或假定 `subagent`、`subagent_fork`、`workflow` 一定已装载。

## 从零开始的推荐路径

1. 先用当前 Harness 的默认 agent 完成一个代表性任务，找出真实瓶颈。
2. 若痛点是反复解释同一流程/规范，先固化为 skill 或项目指令。
3. 若痛点是稳定角色、模型、工具或权限组合，再考虑 agent/preset。
4. 只有在隔离上下文、并行探索或独立执行明显有收益时才委派，并定义好输入与结果。
5. 大规模重复或扇出时，确认平台确有合适编排能力后再引入 workflow/脚本。
6. 用小范围任务验证实际触发、上下文、结果与权限语义，再逐步扩展；不要一开始堆出一组 agent。
